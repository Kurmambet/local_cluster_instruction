# Рубрика: вопрос - ответ

Инвентарь — это не наблюдение за машинами. Это список «кого и как» подключать, плюс переменные для них. Ansible ничего не отслеживает и не держит соединений: он заходит по SSH только в момент запуска. Ниже разбор по твоим вопросам по порядку.

## Что делает инвентарь

**Иерархия влияет на работу, а не только на удобство.** Группы нужны для трёх вещей:

- **Выбор целей.** `hosts: k8s` в плейбуке, `ansible workers -m ping` или `--limit w1` берут машины по имени группы.
- **Наследование переменных.** Переменные группы достаются всем её хостам. Так `ansible_user` из `all.vars` получили все три ноды. Порядок приоритетов описан в документации: переменные хоста перекрывают переменные группы. [docs.ansible](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_variables.html)
- **Магические переменные.** `groups` (словарь «группа → список хостов») и `group_names` (группы текущего хоста) строятся из этой структуры. [docs.ansible](https://docs.ansible.com/projects/ansible/latest/reference_appendices/special_variables.html)

Команда `ansible-inventory --graph` — всего лишь просмотр структуры, на работу плейбуков она не влияет .

**Что ты видишь в выводе.** `@all` и `@ungrouped` — встроенные группы. В `all` входят все хосты, а в `ungrouped` — те, что не состоят ни в одной другой группе. У тебя она пуста, и это нормально.

**Зачем `@k8s` с дочерними группами.** Это не про несколько кластеров. Один и тот же хост может входить в несколько групп, поэтому `cp1` показан дважды: в `control_plane` и в `k8s`, но это одна машина. Группа `k8s` — удобное имя «все ноды кластера»: без неё пришлось бы писать `hosts: control_plane:workers`. Когда понадобятся задачи только для control plane или только для воркеров, ты используешь узкие группы. Если появится второй кластер, добавишь, например, `k8s_dev` со своими детьми. Насколько я знаю, Kubespray делает похоже: у него общая группа кластера включает группы control plane и воркеров.

## Как плейбук находит машины

В задаче `ansible.builtin.ping` адресов нет, потому что адреса в задачах вообще не пишут. Выбор идёт на уровне плея: `hosts: k8s` означает «выполнить все задачи на каждом хосте этой группы». Адрес для подключения Ansible берёт из `ansible_host`, а если его нет, то из `inventory_hostname`. Логин берётся из `ansible_user`. [docs.ansible](https://docs.ansible.com/projects/ansible/latest/reference_appendices/special_variables.html)

Важная деталь: `ansible.builtin.ping` — не ICMP-пинг. Это модуль, который проверяет, что SSH-вход работает и на машине есть Python, и отвечает `pong`. Настоящий пинг между нодами делает только последняя задача, через обычную команду `ping`.

**Откуда `inventory_hostname`.** Это магическая переменная: её задаёт сам Ansible, и перезаписать её нельзя. Она содержит имя текущего хоста так, как оно записано в инвентаре (`cp1`, `w1`, `w2`). Это не то же самое, что системное имя: оно лежит в фактах, например в `ansible_facts['hostname']`. У тебя они совпадают, потому что cloud-init установил `hostname: ${each.key}`, а имена в инвентаре тоже `cp1`, `w1`, `w2`. Если бы ты назвал хост в инвентаре `kc-cp1`, они различались бы. [docs.ansible](https://docs.ansible.com/projects/ansible/latest/reference_appendices/special_variables.html)

**Откуда это знать.** Только из документации: список магических переменных есть на странице Special Variables, а факты и магические переменные описаны в разделе про переменные. Есть и практичный способ смотреть самому: [docs.ansible](https://docs.ansible.com/projects/ansible/latest/reference_appendices/special_variables.html)

```bash
ansible-inventory --host cp1                     # все переменные хоста из инвентаря
ansible cp1 -m ansible.builtin.setup | less      # все факты
ansible-doc ansible.builtin.apt                  # документация модуля прямо в терминале
```

Запуск `hostname` и вывод результата тоже возможен, но хуже: это отдельный SSH-вызов, результат нужно сохранять через `register`, а для `command` придётся ещё писать `changed_when: false`. Общий принцип: если нужное значение есть в фактах или переменных, бери его оттуда, а `command` оставляй для случаев без готового модуля.

## YAML-синтаксис и Python на ВМ

**Что такое `>-`.** Это синтаксис YAML, а не Ansible. Символ `>` создаёт «сложенный» блок: переносы строк превращаются в пробелы, и несколько строк в файле образуют одну строку. Символ `-` убирает завершающий перенос строки. Без него в конец сообщения добавился бы `\n`. Если тебе нужны переносы, используй `|`, он сохраняет строки как есть. Есть и практическая причина: значение, начинающееся с `{{ ... }}`, в YAML обязательно брать в кавычки [docs.ansible](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_variables.html), а в блоке с `>-` кавычки не нужны.

**Откуда Python на ВМ.** Ansible работает так: копирует небольшую Python-программу (модуль) на целевую машину, запускает её там и разбирает ответ. Python на машине действительно нужен, и ты его не ставил, потому что он уже был в образе Ubuntu. Строка `interpreter_python = auto_silent` ничего не устанавливает. Она управляет только поиском: при первом запуске модуля Ansible ищет подходящий интерпретатор из списка обычных путей, а `auto_silent` делает то же самое, что `auto`, но без предупреждений. Результат поиска был виден в выводе ping: `discovered_interpreter_python: /usr/bin/python3.12`. [oneuptime](https://oneuptime.com/blog/post/2026-02-21-configure-ansible-python-interpreter/view)

Если бы Python не было (минимальные образы), его ставят модулем `raw`, который работает без Python. Для модуля `apt` на Ubuntu нужен ещё пакет `python3-apt`, и в cloud-образе он есть. [oneuptime](https://oneuptime.com/blog/post/2026-02-21-configure-ansible-python-interpreter/view)

## apt и state: present

Модуль `ansible.builtin.apt` — это описание желаемого состояния, а не команда. Он сам проверяет, что установлено, и устанавливает только недостающее. Поэтому он лучше, чем `command: sudo apt install ...`:

- **Идемпотентность.** Модуль возвращает `ok`, если пакеты уже есть, и `changed`, если установил. Команда `apt install` всегда считалась бы «изменением», если не дописывать `changed_when`.
- **Режим проверки.** С `--check` модуль честно скажет, что изменилось бы. Команда в этом режиме просто пропускается (как у тебя была задача с пингом).
- **Структурированный результат и абстракция.** Есть понятные ошибки, а при смене системы можно заменить модуль на `dnf` или универсальный `package`.

`state: present` значит «пакет должен быть установлен». Рядом есть `absent` (удалить) и `latest` (обновить до последней версии). В твоём прогоне задача показала `ok`: пакеты уже стояли.

## Цикл по k8s_ip

Переменной `item` у машин нет. Здесь работают два независимых механизма:

1. `loop: "{{ groups['k8s'] }}"`. Магическая переменная `groups['k8s']` — это список `['cp1', 'w1', 'w2']`. Ключевое слово `loop` повторяет задачу по одному разу для каждого элемента. Переменную `item` Ansible создаёт автоматически и кладёт в неё текущий элемент. То есть `item` по очереди равна `cp1`, `w1`, `w2`. [docs.ansible](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_loops.html)
2. `hostvars[item]['k8s_ip']`. Магическая переменная `hostvars` — словарь «хост → его переменные». Значение `hostvars['cp1']['k8s_ip']` — это `10.10.10.11`, которое ты сам записал в `inventory.yml` для `cp1`. Это обычная переменная хоста, а не список. [docs.ansible](https://docs.ansible.com/projects/ansible/latest/reference_appendices/special_variables.html)

Поэтому при `item = cp1` команда превращается в `ping -c 1 -W 2 10.10.10.11`, при `w1` — в `10.10.10.12`, и так далее.

Теперь посчитаем повторения: плей запускает каждую задачу на каждом из трёх хостов, а цикл внутри перебирает три адреса. В итоге выполняется девять пингов: каждая нода проверяет связь с каждой, включая себя. Именно эти девять пар ты видел в первом `--check` (тогда они были пропущены). Чтобы увидеть данные до запуска, добавь отладочную задачу или выполни команду:

```bash
ansible k8s -m ansible.builtin.debug -a "var=groups"
```

Она покажет весь словарь групп, из которого строится цикл.
