На хосте появились три вида интерфейсов, которых раньше не было: мосты `virbr*`, виртуальные кабели `vnet*` и Docker. Диск cloud-init нужен, потому что Terraform создаёт «железо» ВМ, а настраивать систему внутри должен сам гость при первой загрузке. Ниже: сначала интерфейсы, потом cloud-init, потом ход `apply`, потом разбор каждой строки `main.tf`.

## Откуда столько интерфейсов

Это не лишние адаптеры, а устройства, которые создал libvirt:

| Интерфейс                | Что это                                                                                                                                                                                             |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `enp7s0`, `wlp8s0`       | Реальные сетевые карты (проводная и Wi-Fi), обе в `192.168.1.x`                                                                                                                                     |
| `docker0`, `veth11f59ca` | Мост Docker и «кабель» к запущенному контейнеру                                                                                                                                                     |
| `virbr0`                 | Сеть `default`, которую libvirt создаёт при установке: NAT на `192.168.122.0/24` [wiki.libvirt](https://wiki.libvirt.org/Networking.html). Статус `NO-CARRIER`, потому что к ней никто не подключён |
| `virbr1`                 | Твоя сеть `k8s-mgmt`: мост с адресом `192.168.100.1`                                                                                                                                                |
| `virbr2`                 | Твоя сеть `k8s-net`: мост с адресом `10.10.10.1`                                                                                                                                                    |
| `vnet0`…`vnet5`          | По одному виртуальному «кабелю» (tap) на каждую сетевую карту каждой ВМ: 3 ВМ × 2 карты = 6                                                                                                         |

Мост — это виртуальный коммутатор: ВМки подключаются к нему и общаются через него, а на хосте он виден как обычный интерфейс. Адрес `.1` на мосту — это одновременно адрес хоста в этой сети и шлюз для ВМ. Поэтому SSH с хоста на `192.168.100.11` работает напрямую, без проброса портов. [wiki.libvirt](https://wiki.libvirt.org/VirtualNetworking.html)

Соответствие видно по MAC-адресам. Например, `vnet2` (`fe:54:00:aa:01:01`) подключён к `virbr1`, значит, это первая карта `cp1`. А `vnet4` — вторая карта `cp1` в `virbr2`. Проверить можно командой `virsh -c qemu:///system domiflist cp1`. Интерфейсы `vnetN` появляются при старте ВМ и исчезают при остановке.

Изолированная сеть (`mode = "none"`) изолирована от внешнего мира, но не от хоста: гости говорят друг с другом и с хостом, а наружу трафик не выходит. NAT-сеть `k8s-mgmt` пропускает исходящий трафик ВМ в интернет через хост, а входящие подключения снаружи запрещены. [wiki.libvirt](https://wiki.libvirt.org/VirtualNetworking.html)

## Зачем нужен cloud-init диск

Здесь нет дублирования, а два разных уровня. Terraform через libvirt описывает виртуальное железо: сколько памяти и ядер, какой блочный диск, какие карты с какими MAC. Но образ Ubuntu внутри диска общий и безликий: в нём нет ни пользователя, ни твоего SSH-ключа, ни IP-адресов, ни имени хоста. Terraform не может «зайти внутрь» ещё не запущенной системы. Единственный канал от гипервизора к гостю при загрузке — виртуальное железо.

Cloud-init использует именно этот канал. В образе Ubuntu есть служба cloud-init. При первой загрузке она ищет диск с меткой `cidata` (источник данных NoCloud) и читает с него файлы `user-data`, `meta-data` и необязательный `network-config`. Ресурс `libvirt_cloudinit_disk` собирает такой ISO-образ (для этого и ставился `genisoimage`) и подключает его как CD-привод. В VirtualBox ты делал то же вручную: заходил в консоль и правил `/etc/netplan/00-installer-config.yaml`. Cloud-init делает это за тебя при первом старте. [docs.cloud-init](https://docs.cloud-init.io/en/latest/reference/datasources/nocloud.html)

Хороший пример разделения уровней — диск. `libvirt_volume.size` задаёт размер блочного устройства в 20 ГБ. А расширение раздела и файловой системы до 20 ГБ выполняет cloud-init внутри гостя при первой загрузке (`df` показал 19 ГБ).

Дублирование всё же есть, и оно двух видов:

- **MAC-адрес** задан и для виртуальной карты (в `libvirt_domain`), и для сопоставления в netplan (в `network_config`). Это намеренно: имена вроде `enp0s3` зависят от порядка устройств и могут меняться, а MAC стабилен. Чтобы не вводить его дважды руками, он хранится один раз в `locals.nodes`.
- **Подсеть и шлюз.** `192.168.100.0/24` записано в сети, а `192.168.100.1` — в `routes`. Это настоящее дублирование, его можно убрать, вынеся CIDR в `locals` и вычисляя шлюз функцией `cidrhost()`.

Есть и другой вариант дизайна: не задавать IP через netplan, а сделать DHCP-резервации в самой сети libvirt по MAC (в сети включается DHCP и добавляются записи `host mac=... ip=...`). Тогда `network_config` не нужен, а в cloud-init остаётся только `user_data` (пользователь и ключ). Я выбрал статику в netplan, чтобы повторить схему из твоей инструкции для VirtualBox и чтобы адрес был виден в одном месте. [cubepath](https://cubepath.com/docs/virtualization-vps/virtual-network-configuration-with-libvirt)

Важная особенность: cloud-init считает «первой загрузкой» момент, когда меняется `instance-id`. Если после запуска ты поменяешь `user_data` или `network_config`, система внутри уже работающей ВМ их не применит. Нужно пересоздать ВМ командой `terraform apply -replace='libvirt_domain.vm["cp1"]'`. [docs.cloud-init](https://docs.cloud-init.io/en/latest/reference/datasources/nocloud.html)

## Что происходит при terraform apply

**Сначала граф.** Terraform строит граф зависимостей по ссылкам между ресурсами. Ссылка вида `libvirt_network.mgmt.id` внутри домена означает «сначала создай сеть». Порядок блоков в файле не важен. Независимые ресурсы создаются параллельно, по умолчанию до 10 одновременно. Это видно в твоём логе: сети и пул стартовали одновременно. [developer.hashicorp](https://developer.hashicorp.com/terraform/internals/graph)

```
Волна 1:  libvirt_pool         libvirt_network.mgmt     libvirt_network.k8s
              |
Волна 2:  base-образ (скачивание)    cloud-init диски ×3 (генерация ISO)
              |
Волна 3:  disk cp1/w1/w2 (20 ГБ, поверх base)
              |
Волна 4:  libvirt_domain ×3 (определение и запуск ВМ)
```

**Волна 1.**

- Пул: libvirt создаёт каталог `/var/lib/libvirt/k8s-lab` для дисков.
- Сеть `k8s-mgmt` (NAT): создаётся мост `virbr1`, на него вешается `192.168.100.1/24`, запускается `dnsmasq` и добавляются правила NAT (маскарадинг). DHCP выключен, но DNS на `.1` работает, поэтому он и указан в `nameservers`. [libvirt](https://libvirt.org/formatnetwork.html)
- Сеть `k8s-net` (изолированная): создаётся мост `virbr2` с адресом `10.10.10.1/24` без правил NAT и пересылки наружу.

**Волна 2.**

- Базовый образ: провайдер скачивает `.img` по URL и загружает его в пул как qcow2. В логе это 59 секунд. Файл занимает 597 МБ, виртуальный размер 3,5 ГБ.
- Cloud-init диски: провайдер подставляет значения в `user_data` и `network_config`, собирает ISO с меткой `cidata` и кладёт его в пул.

**Волна 3.** Для каждой ВМ создаётся диск на 20 ГБ в режиме copy-on-write: это тонкий файл (около 196 КБ), который ссылается на base-образ как на backing-файл. Все три ВМ читают общий образ и записывают только свои изменения. Это подтвердил твой `qemu-img info --backing-chain`.

**Волна 4.** Для каждой ВМ libvirt получает XML-описание: 2048 МБ, 2 vCPU, диск `vda`, ISO как CD-привод, две virtio-карты с заданными MAC и привязкой к мостам. Затем:

- libvirt создаёт tap-устройства `vnetN` и подключает их к `virbr1` и `virbr2`;
- применяет защитный драйвер (здесь у тебя была ошибка прав);
- запускает процесс QEMU.

**Что происходит внутри ВМ.** При первой загрузке ядро стартует, затем cloud-init находит CD с меткой `cidata` и:

- читает `network-config`, пишет netplan, находит карты по MAC, переименовывает их в `nic0` и `nic1` и назначает IP;
- читает `user-data`: ставит hostname, создаёт пользователя `ubuntu` с ключом и правами sudo;
- расширяет раздел и файловую систему до 20 ГБ.

После этого SSH принимает подключения, а Terraform в конце печатает `output`.

## Построчный разбор main.tf

**Блок terraform и provider**

| Строка                         | Зачем                                                                                                                                   |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| `source = "dmacvicar/libvirt"` | Адрес провайдера в реестре; `terraform init` скачает его                                                                                |
| `version = "~> 0.8.3"`         | Допустимы 0.8.3 и новее, но ниже 0.9.0. Защита от несовместимой версии 0.9.x                                                            |
| `uri = "qemu:///system"`       | Подключение к системному демону libvirtd. Нужен он, потому что создание мостов и NAT требует привилегий, а доступ даёт группа `libvirt` |

**Блок locals**

| Строка                                       | Зачем                                                                                                    |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `ssh_pubkey = file("~/.ssh/id_ed25519.pub")` | Читает публичный ключ с диска при планировании                                                           |
| `nodes = { cp1 = {...}, ... }`               | Единственный источник правды о ВМ: ключи (`cp1`, `w1`, `w2`) станут именами, а значения — адресами и MAC |
| `ip_mgmt`, `ip_k8s`                          | IP на первой (NAT) и второй (изолированной) сети                                                         |
| `mac_mgmt`, `mac_k8s`                        | MAC для сопоставления; префикс `52:54:00` принят в QEMU/KVM, `aa` и `bb` различают сети                  |

**libvirt_pool**: `name` — имя в libvirt, `type = "dir"` — хранилище в обычной папке, `path` — её адрес. Параметр `path` в новых версиях провайдера объявлен устаревшим, отсюда предупреждение.

**libvirt_network (оба)**

| Строка                     | Зачем                                                  |
| -------------------------- | ------------------------------------------------------ |
| `name`                     | Имя сети в libvirt                                     |
| `mode = "nat"` / `"none"`  | NAT с выходом в интернет или полная изоляция           |
| `addresses = [...]`        | Подсеть. Хост получает первый адрес (`.1`), он же шлюз |
| `dhcp { enabled = false }` | Адреса раздаём сами через cloud-init, DHCP не нужен    |

**libvirt_volume.base**: `source` — URL образа (`noble/current` обновляется со временем, но Terraform не скачает заново, пока URL не изменился), `format = "qcow2"` — формат с поддержкой backing-файла.

**libvirt_volume.disk**

| Строка                           | Зачем                                                            |
| -------------------------------- | ---------------------------------------------------------------- |
| `for_each = local.nodes`         | Создать по диску на каждую запись, обращение `each.key` даёт имя |
| `base_volume_id`                 | Ссылка на base-образ; создаёт и зависимость, и backing-файл      |
| `size = 20 * 1024 * 1024 * 1024` | 20 ГБ в байтах (в плане: 21474836480)                            |

**libvirt_cloudinit_disk**

| Строка                                 | Зачем                                                                                                     |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `user_data = <<-EOF`                   | Блок многострочного текста; `-` убирает общий отступ                                                      |
| `#cloud-config`                        | Обязательная первая строка: по ней cloud-init узнаёт формат                                               |
| `hostname`, `manage_etc_hosts: true`   | Имя хоста и запись в `/etc/hosts`, чтобы `sudo` не ругался на имя                                         |
| `users: ... ubuntu`                    | Создаёт пользователя; `sudo: ALL=(ALL) NOPASSWD:ALL` даёт sudo без пароля                                 |
| `lock_passwd: true`                    | Вход по паролю закрыт, остаётся только ключ                                                               |
| `ssh_authorized_keys`                  | Твой публичный ключ из `locals`                                                                           |
| `network_config` (`version: 2`)        | Синтаксис netplan; `nic0` и `nic1` — просто метки                                                         |
| `match.macaddress` + `set-name`        | Найти карту по MAC и дать ей имя `nic0`/`nic1`                                                            |
| `dhcp4: false`, `addresses`            | Статический IP                                                                                            |
| `routes: to default via 192.168.100.1` | Маршрут по умолчанию только у `nic0`, поэтому интернет идёт через NAT, а `nic1` остаётся сетью Kubernetes |
| `nameservers`                          | DNS libvirt на `.1` и запасной `1.1.1.1`                                                                  |

**libvirt_domain**

| Строка                          | Зачем                                                                               |
| ------------------------------- | ----------------------------------------------------------------------------------- |
| `memory = 2048`, `vcpu = 2`     | МБ ОЗУ и число ядер                                                                 |
| `cloudinit = ...id`             | Подключает ISO как CD-привод                                                        |
| `network_interface` (два блока) | Порядок блоков = порядок карт: первая стала `enp0s3`/`nic0`, вторая `enp0s4`/`nic1` |
| `network_id`, `mac`             | К какой сети подключить и с каким MAC                                               |
| `disk { volume_id }`            | Подключает диск как `vda`                                                           |
| `console { type = "pty" ... }`  | Последовательная консоль, благодаря ей работает `virsh console`                     |

В `output "ssh"` словарь собирается циклом `for`; это только подсказка при выводе, ресурсов она не создаёт.

Ещё несколько значений ты не писал, но провайдер подставил их сам: тип `kvm`, `running = true`, `qemu_agent = false`. Он также добавил графику SPICE и видеокарту `cirrus-vga`. В журнале QEMU это видно по порту 5902. Для серверных ВМ графика не нужна, и при желании её можно убрать отдельным блоком. Это даст небольшую экономию ресурсов.
