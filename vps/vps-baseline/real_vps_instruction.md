Почти всё верно, но в нескольких местах стоит уточнить. Ниже по порядку.

## Почему задачи skipped

Это не «уже выполнено»: выполненная задача показывала бы `ok`. Пропуск означает, что условие `when` ложно. На реальном сервере выполнятся только те задачи, у которых условие станет истинным:

| Задача                   | Почему пропущена в лаборатории                                                                        | Когда выполнится                        |
| ------------------------ | ----------------------------------------------------------------------------------------------------- | --------------------------------------- |
| hostname                 | `base_set_hostname: false` по умолчанию                                                               | Если включишь переменную                |
| swap и swappiness        | В `host_vars/lab-vm.yml` я поставил `base_swap_size_mb: 0`, чтобы на этих ВМ потом работал Kubernetes | На сервере с ОЗУ меньше 4 ГБ и без swap |
| SSH-ключи для деплоя     | `deploy_ssh_public_keys` пуст                                                                         | Когда добавишь публичный ключ CI        |
| Сообщение о перезагрузке | Файла `/var/run/reboot-required` нет                                                                  | Когда обновится ядро                    |
| certbot                  | `tls: false` и пустой email                                                                           | Когда включишь TLS                      |
| `app_dirs`               | Список `apps` пуст                                                                                    | Когда опишешь проекты                   |

## TLS и certbot

В лаборатории не проверен не только выпуск сертификата, а вся TLS-ветка: HTTPS-блок, редирект, HSTS, заглушка 503, `ssl_reject_handshake`, basic auth для Grafana, роль `app_dirs`. Первый запуск на реальном сервере поэтому лучше сделать на `certbot_staging: true`: тестовое окружение Let's Encrypt выдаёт сертификаты, которым браузеры не доверяют, зато оно защищает от упора в лимиты. Боевые лимиты строгие: до 5 сертификатов на один и тот же набор доменов в неделю и до 5 неудачных проверок в час. [letsencrypt](https://letsencrypt.org/docs/staging-environment/)

Есть подвох с переключением. Задача certbot в роли имеет `creates:` на файл сертификата, а certbot запоминает сервер в конфиге обновления сертификата. Если после staging поставить `certbot_staging: false`, Ansible увидит существующий файл и ничего не выпустит, а certbot будет продлевать тестовый сертификат. Сначала удали его: [codewithkarani](https://www.codewithkarani.com/blog/certbot-default-to-letsencrypt-staging)

```bash
ssh devops@сервер 'sudo certbot delete --cert-name example.com'
```

Затем выставь `false` и запусти плейбук ещё раз. Условия для успеха: A-записи домена и `www` указывают на сервер, порты 80 и 443 открыты не только в UFW, но и в файрволе провайдера, заполнены `certbot_email` и `tls: true`.

## Секреты и инвентарь

Не всё нужно прятать в vault. Он нужен только для секретов: паролей, токенов, приватных ключей. Домен, почта, IP, имя пользователя и публичные ключи секретом не являются (домен всё равно виден в сертификате). Если вынести их в vault, изменения станут нечитаемыми, а безопасности не прибавится. Хранить такие значения лучше в `host_vars/prod1.yml` (для конкретного сервера) и в `group_vars` (для общих настроек). Если репозиторий публичный, просто не публикуй инвентарь и `host_vars`: это вопрос приватности, а не защиты.

С паролем от провайдера лучше вообще не работать через файлы. Один раз добавь свой ключ командой `ssh-copy-id root@IP`, и дальше `bootstrap.yml` пойдёт по ключу. Если всё же нужен пароль, есть два варианта: `--ask-pass` (вводишь вручную, ничего не хранится) или переменная из vault по схеме `ansible_password: "{{ vault_ansible_password }}"`. SSH-ключи Ansible рекомендует по умолчанию, пароль допускается как временная мера. В твоей версии ansible-core 2.21 пароль по умолчанию передаётся через `ssh_askpass`, так что `sshpass` может быть и не нужен. После `bootstrap.yml` меняй `ansible_user` на `devops`: пароль и root-вход будут уже закрыты. [ansiblepilot](https://www.ansiblepilot.com/articles/ansible-ssh-password-authentication-sshpass-connection-setup-guide)

Для реального сервера примерно так:

```yaml
# inventory/hosts.yml
prod1:
  ansible_host: 203.0.113.10
  ansible_user: devops # для bootstrap.yml: запуск с -u root
```

В vault попадают: `nginx_basic_auth_password`, пароли БД, `APP_SECRET_KEY`, пароль админа Grafana и, если используешь пароль для первого входа, `vault_ansible_password`.

## CI/CD и ручной деплой

Да, сам CI/CD в плейбуках описывать не нужно. Ansible только готовит для него основу: пользователя `deploy`, группу `docker`, каталог `/opt/<проект>` с env-файлами, виртуальные хосты nginx и открытые порты. Связующие звенья: `deploy_ssh_public_keys` (публичная часть ключа CI), `apps[].env_files` (секреты) и `nginx_sites` (порты, которые compose публикует на `127.0.0.1`). Для CI создай отдельный ключ, публичную часть добавь в `deploy_ssh_public_keys`, а приватную положи в секрет GitHub `DEPLOY_SSH_PRIVATE_KEY`. Значение для `DEPLOY_KNOWN_HOSTS` получи командой `ssh-keyscan -t ed25519 host` с сервера, который уже существует.

А вот вывод про ручной деплой неверен: деплоить вручную можно и нужно уметь. Ansible не агент и не демон: он ничего не блокирует и работает только в момент запуска. Заходи под `devops` или `deploy` и выполняй `docker compose` в `/opt/<проект>`. Нельзя другое: править вручную файлы, которыми управляет Ansible. Это конфиги nginx и сниппеты, drop-in sshd, jail fail2ban, `daemon.json`, правила UFW и env-файлы из списка `apps`. Следующий запуск плейбука перезапишет их, поэтому такие изменения вноси в переменные и шаблоны. Compose-файл, `images.env`, контейнеры и тома Ansible не трогает, ими можно управлять свободно.

## Порядок для реального сервера

1. Создай A-записи домена и проверь, что порты 80 и 443 открыты у провайдера.
2. Выполни `ssh-copy-id root@IP`, затем `ansible-playbook bootstrap.yml -u root --limit prod1`.
3. В отдельном терминале проверь вход `ssh devops@IP`, потом поменяй `ansible_user` на `devops`.
4. Запусти `ansible-playbook site.yml --limit prod1` с `certbot_staging: true`.
5. Проверь сайт, затем удали тестовый сертификат (команда выше), поставь `certbot_staging: false` и запусти плейбук ещё раз.
6. Положи в GitHub-секреты данные для CI и проверь деплой.
